# ADR-002 — Shared Database / Shared Schema Multi-Tenancy

## Status

Accepted for initial architecture

## Context

The platform is SaaS and must host multiple independent businesses while strictly isolating their data.

For the initial product, operational simplicity and cost efficiency are important.

## Decision

The initial architecture uses a shared database and shared schema with explicit tenant ownership on shop-owned records, represented by `shop_id` in the current product requirements.

The logical rule is:

```text
1 Shop = 1 Tenant
```

for the MVP working model.

All tenant-owned reads and writes must execute inside a validated tenant context.

## Alternatives Considered

### Schema per Tenant

Provides stronger physical separation but introduces more operational and migration complexity for an early-stage SaaS.

### Database per Tenant

Provides strong isolation but is operationally expensive and unnecessary for the initial scale assumptions.

## Consequences

### Positive

- Lower operational complexity
- Lower infrastructure cost
- Simpler initial deployment
- Straightforward tenant-aware querying
- Can evolve later if scale/compliance requires it

### Negative

- Isolation depends heavily on application correctness
- Missing tenant filters can become serious security defects
- Tenant-aware testing and constraints are mandatory

## Required Safeguards

- Server-controlled tenant context
- Tenant-aware repositories/data access
- Resource-level tenant validation
- Automated cross-tenant tests
- Auditing of exceptional administrative access

## Revisit Conditions

Revisit this decision if requirements introduce major compliance constraints, very large tenant scale, regional data residency requirements, or another requirement that makes stronger physical isolation necessary.
