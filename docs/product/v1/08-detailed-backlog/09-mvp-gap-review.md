# بازبینی شکاف‌های MVP

## 1. هدف

هدف این سند بازبینی کل MVP پس از تکمیل Golden Flowهای اصلی است تا مشخص شود آیا پیش از تبدیل User Storyها به Issueهای اجرایی، قابلیت مشترک، وابستگی یا جریان ضروری‌ای باقی مانده است یا خیر.

این سند Golden Flow جدید تعریف نمی‌کند؛ تمرکز آن روی قابلیت‌های مشترک، جریان‌های مکمل و الزامات سراسری محصول است.

---

## 2. نتیجه بازبینی

### نتیجه کلی

هشت Golden Flow اصلی، ستون فقرات کسب‌وکاری MVP را پوشش می‌دهند:

1. خرید → موجودی → بستانکاری → حسابداری
2. فروش → موجودی → بدهکاری → دریافت → حسابداری
3. بانک → تطبیق → حسابداری
4. هزینه → پرداخت/بستانکاری → حسابداری
5. کنترل مالی → بستن دوره
6. حقوق → بیمه → حسابداری
7. مالیات و صورتحساب الکترونیکی → حسابداری
8. دارایی ثابت → استهلاک → حسابداری

با این حال، برای اینکه محصول واقعاً توسط یک شرکت استفاده شود، چند قابلیت مشترک باید به‌صورت مستقل در بک‌لاگ MVP تثبیت شوند.

### نتیجه اصلی

هیچ Golden Flow نهمی در این مرحله ضروری نیست؛ اما قبل از ورود جدی به Issue Breakdown، این دسته‌ها باید وارد بک‌لاگ شوند:

- هویت، شرکت و دسترسی
- راه‌اندازی و ورود اطلاعات اولیه
- هسته حسابداری
- موتور اجرای عملیات و تأیید
- اسناد، فایل‌ها و ردیابی ارتباط داده‌ها
- انبار و عملیات مکمل
- گزارش، جستجو و خروجی
- اعلان و کنترل
- Agent Platform مشترک
- Adapter/Provider Platform
- Rule Engine
- امنیت، پایداری، پشتیبان‌گیری و بازیابی

---

# 3. شکاف‌های ضروری MVP

## 3.1 هویت، شرکت، عضویت و دسترسی

**اولویت: Critical**

در حال حاضر نقش‌ها و اصول دسترسی تعریف شده‌اند، اما باید قابلیت اجرایی آن‌ها به‌صورت مستقل در بک‌لاگ تثبیت شود.

### باید وجود داشته باشد

- ورود و خروج کاربر
- ایجاد/دعوت کاربر
- عضویت کاربر در شرکت
- نقش کاربر در شرکت
- مدیریت دسترسی بر اساس حوزه و عملیات
- محدودیت دسترسی به داده‌های همان شرکت
- تفکیک حسابدار، مدیر مالی، مدیرعامل، کاربر عملیاتی و مدیر سیستم
- ثبت تغییر نقش و دسترسی
- لغو دسترسی
- کنترل دسترسی هنگام اجرای Agent و عملیات دستی

### نکته

در MVP هر کاربر می‌تواند فقط عضو یک شرکت باشد، اما مدل باید از ابتدا Membership را به‌عنوان موجودیت مستقل نگه دارد تا چندشرکتی در آینده نیازمند بازطراحی نباشد.

---

## 3.2 راه‌اندازی شرکت و اطلاعات اولیه

**اولویت: Critical**

یک شرکت واقعی از روز صفر همیشه همه داده‌هایش را از Flowهای جدید وارد نمی‌کند. باید بتواند اطلاعات اولیه را وارد کند.

### باید وجود داشته باشد

- ساخت شرکت
- اطلاعات پایه شرکت
- سال مالی و دوره‌های مالی
- تنظیمات پایه شرکت
- کدینگ حساب‌ها
- طرف‌حساب‌های اولیه
- کالاها و خدمات اولیه
- موجودی اولیه
- مانده بانک و صندوق
- مانده دریافتنی و پرداختنی
- دارایی‌های موجود از قبل
- مانده‌های افتتاحیه حساب‌ها
- وارد کردن اطلاعات از Excel
- اعتبارسنجی و گزارش خطا قبل از ثبت
- ثبت سابقه ورود اطلاعات اولیه

### اصل مهم

ورود اطلاعات اولیه باید بتواند یک «برنامه ثبت و اعتبارسنجی» داشته باشد، اما اجرای نهایی آن بدون تأیید کاربر انجام نشود.

---

## 3.3 هسته حسابداری

**اولویت: Critical**

Golden Flowها از حسابداری استفاده می‌کنند، اما هسته حسابداری باید به‌عنوان یک قابلیت مستقل و مشترک تثبیت شود.

### باید وجود داشته باشد

- حساب‌ها و ساختار درختی حساب‌ها
- حساب تفصیلی
- امکان استفاده از کدینگ پیشنهادی یا کدینگ سفارشی
- سند حسابداری
- ردیف سند
- بدهکار/بستانکار
- کنترل تراز سند
- شماره سند
- تاریخ سند
- دوره مالی
- وضعیت سند
- دفتر روزنامه
- دفتر کل
- گردش و مانده حساب
- ارتباط سند با عملیات مبنا
- ارتباط چند سند با یک عملیات واحد
- ثبت سند اصلاحی
- ثبت سند برگشتی/معکوس
- قفل سند ثبت‌شده
- جلوگیری از حذف یا ویرایش مستقیم سند ثبت‌شده

### اصل مهم

هیچ Agent نباید مستقیماً منطق حسابداری را اجرا کند. Agent فقط برنامه می‌سازد و هسته حسابداری اعتبارسنجی و اجرا را انجام می‌دهد.

### باید وجود داشته باشد

- الگوی شماره‌گذاری قابل تنظیم
- کنترل تکراری نبودن شماره

## 3.5 موتور اجرای برنامه و تأیید

**اولویت: Critical**

الگوی مشترک Agent در چندین Flow تکرار شده و باید به‌صورت یک قابلیت مشترک ساخته شود.

### مدل استاندارد

```text
درخواست کاربر
↓
تحلیل
↓
برنامه عملیات
↓
نمایش اثرات
↓
ویرایش کاربر
↓
تأیید
↓
اعتبارسنجی دامنه
↓
اجرا
↓
اعتبارسنجی نتیجه
↓
ثبت Audit Log
```

### باید وجود داشته باشد

- Plan
- Action
- Dependency بین Actionها
- وضعیت Plan
- وضعیت هر Action
- پیش‌نمایش اثرات
- ویرایش Plan
- تأیید Plan
- اعتبارسنجی نهایی قبل از اجرا
- اجرای اتمیک در حد ممکن
- مدیریت خطا
- جلوگیری از اجرای دوباره
- امکان ادامه از وضعیت کنترل‌شده در صورت شکست
- نمایش نتیجه هر Action
- نمایش عملیات ناقص
- جلوگیری از وضعیت «ظاهراً موفق ولی واقعاً ناقص»

## 3.6 Audit Log سراسری

**اولویت: Critical**

Audit در Flowها مطرح شده است اما باید یک قابلیت مشترک باشد.

### باید ثبت شود

- چه کسی
- چه زمانی
- روی چه شرکت
- چه عملیاتی
- روی چه موجودیتی
- مقدار قبل
- مقدار بعد
- علت تغییر
- منبع تغییر: دستی / Agent / سیستم / Adapter
- Plan مربوطه
- Action مربوطه
- نتیجه
- خطا
- علت شکست

### اصل مهم

Audit Log قابل حذف یا ویرایش توسط کاربر عادی نباشد.

### باید وجود داشته باشد

- آپلود فایل
- نگهداری فایل اصلی
- نگهداری نسخه پردازش‌شده
- اتصال فایل به عملیات
- اتصال فایل به سند حسابداری
- اتصال فایل به طرف‌حساب
- اتصال فایل به Agent Run
- تاریخ و منبع فایل
- وضعیت استخراج
- خطاهای استخراج
- مشاهده و دانلود فایل
- جلوگیری از گم‌شدن رابطه فایل و عملیات

### فرمت‌های MVP

حداقل PDF، تصویر و Excel/CSV بر اساس Flow مربوطه.

## 3.9 انبار و عملیات مکمل

**اولویت: Critical**

در MVP چند انبار داریم، اما صرفاً دریافت و خروج کالا کافی نیست.

### موارد ضروری

- انتقال بین انبارها
- اصلاح موجودی
- شمارش/انبارگردانی
- ثبت مغایرت موجودی
- تاریخچه گردش کالا
- مانده موجودی هر انبار
- کنترل موجودی منفی طبق سیاست شرکت
- محاسبه بهای موجودی بر اساس روش انتخاب‌شده
- ارتباط عملیات انبار با حسابداری

### موارد خارج از MVP

- بارکد پیشرفته
- سریال‌گذاری پیچیده
- ردیابی چندلایه Batch/Lot در حد سازمان‌های بزرگ
- WMS کامل

## 3.10 Returns و عملیات برگشتی

**اولویت: High**

فروش و خرید بدون سناریوی برگشت ناقص است، اما این مورد الزاماً Golden Flow مستقل نیست.

### نیازمندی

معماری باید پشتیبانی کند از:

- برگشت فروش
- برگشت خرید
- اصلاح اثر موجودی
- اصلاح دریافتنی/پرداختنی
- اصلاح حسابداری
- ارتباط با صورتحساب/اسناد مالیاتی مرتبط

### تصمیم MVP

این قابلیت می‌تواند به‌صورت یک جریان مکمل در MVP اجرا شود؛ لازم نیست Golden Flow مستقل شماره ۹ ایجاد شود.

# 10. جمع‌بندی نهایی

MVP از نظر جریان‌های اصلی کسب‌وکار پوشش دارد، اما «آماده توسعه» بودن فقط با داشتن Golden Flowها محقق نمی‌شود.

بخش مهم بعدی، ساختن قابلیت‌های مشترکی است که همه Flowها بر آن‌ها سوار می‌شوند؛ مخصوصاً:

- هسته حسابداری
- هویت و دسترسی
- شرکت و دوره مالی
- Plan/Approval/Execution
- Audit
- فایل و Import/Export
- Agent Platform
- Rule Engine
- Adapter/Provider
- Idempotency و Recovery
- Initial Setup و Opening Balances
- گزارش و اعلان

پس از ثبت این موارد در بک‌لاگ، می‌توان User Storyها را به Issueهای قابل اجرا برای توسعه Agentic تبدیل کرد، بدون اینکه در میانه توسعه مجبور شویم معماری محصول را به‌دلیل یک قابلیت مشترک بازطراحی کنیم.
