# User Storyهای مشترک و زیرساختی MVP

## 1. هدف سند

این سند شکاف‌های شناسایی‌شده در بازبینی MVP را به User Storyهای مستقل تبدیل می‌کند. این Storyها به Golden Flowهای اصلی وابسته‌اند و بعضی از آن‌ها زیرساخت مشترک چندین Flow هستند.

هدف این سند این است که قبل از ورود به Issue Breakdown، قابلیت‌های مشترک محصول از نظر ارزش کسب‌وکاری، قواعد و معیار پذیرش تثبیت شده باشند.

---

# 2. اصول مشترک این بخش

1. مسیر دستی و مسیر هوشمند باید هر دو وجود داشته باشند.
2. Agent فقط پیشنهاد و Plan ایجاد می‌کند و منطق دامنه را دور نمی‌زند.
3. اجرای عملیات مالی مهم بدون تأیید کاربر مجاز نیست.
4. اسناد ثبت‌شده مستقیم ویرایش یا حذف نمی‌شوند و اصلاح با عملیات اصلاحی انجام می‌شود.
5. همه عملیات مالی و Agent قابل ردیابی و Audit هستند.
6. جداسازی داده شرکت‌ها در تمام لایه‌ها الزامی است.
7. قوانین متغیر نسخه‌پذیرند و داخل منطق ثابت دامنه دفن نمی‌شوند.
8. شکست عملیات باید صریح و قابل مشاهده باشد و هرگز به وضعیت ظاهراً موفق ولی ناقص منجر نشود.

# 3. هویت، شرکت و دسترسی

## IAM-001 — ورود و مدیریت نشست کاربر

**حوزه:** هویت و دسترسی  
**اولویت:** Critical

### داستان کاربر

به‌عنوان کاربر، می‌خواهم به‌صورت امن وارد سیستم شوم و نشست کاربری من کنترل‌شده باشد تا دسترسی غیرمجاز به اطلاعات مالی رخ ندهد.

### هدف

ایجاد پایه امن برای تمام قابلیت‌های محصول.

### پیش‌شرط

کاربر در سیستم ثبت شده باشد.

### جریان اصلی

ورود → اعتبارسنجی → ایجاد نشست → ورود به محیط مجاز شرکت.

### موارد مهم کسب‌وکاری

- نشست باید قابل ابطال باشد.
- خروج کاربر باید نشست جاری را بی‌اعتبار کند.
- دسترسی‌های کاربر در زمان اجرای عملیات بررسی شوند.

### معیارهای پذیرش

- کاربر بدون احراز هویت به داده مالی دسترسی نداشته باشد.
- پس از ابطال نشست، استفاده از آن ممکن نباشد.
- رویدادهای امنیتی مهم ثبت شوند.

### وابستگی‌ها

مدل کاربر، شرکت و عضویت.

### موارد وابسته

SEC-001، AUD-001

### مسیر طلایی

ورود موفق → انتخاب محیط شرکت → مشاهده داشبورد مجاز.

### معیار سرعت

ورود عادی بدون تأخیر محسوس در محیط عملیاتی.

### معیار ثبات داده

هیچ نشست معتبری نباید به داده شرکت دیگر دسترسی داشته باشد.

### معیار تکمیل

احراز هویت، نشست، خروج و رویدادهای امنیتی عملیاتی و قابل Audit باشند.

## IAM-002 — عضویت کاربر در شرکت

**حوزه:** شرکت و Membership  
**اولویت:** Critical

### داستان کاربر

به‌عنوان مدیر شرکت، می‌خواهم کاربر را به شرکت اضافه یا دسترسی او را لغو کنم تا عضویت‌ها کنترل شوند.

### هدف

جدا کردن مفهوم «کاربر» از «عضویت در شرکت» و آماده‌سازی معماری چندشرکتی آینده.

### پیش‌شرط

شرکت وجود داشته باشد و کاربر مجاز به مدیریت اعضا باشد.

### جریان اصلی

دعوت/ایجاد عضویت → تعیین نقش → فعال شدن عضویت → ثبت Audit.

### موارد مهم کسب‌وکاری

- در MVP هر کاربر می‌تواند در یک شرکت عضو فعال داشته باشد.
- Membership موجودیتی مستقل است.
- لغو عضویت نباید سوابق قبلی را حذف کند.

### معیارهای پذیرش

- عضویت قابل ایجاد، فعال، غیرفعال و لغو باشد.
- داده شرکت دیگر برای کاربر قابل مشاهده نشود.
- تغییرات عضویت Audit شوند.

### وابستگی‌ها

IAM-001، SEC-001، AUD-001

### موارد وابسته

IAM-003، IAM-004

### مسیر طلایی

مدیریت اعضا → ایجاد عضویت → نقش → دسترسی → Audit.

### معیار ثبات داده

غیرفعال‌سازی عضویت نباید رکورد مالی تاریخی را حذف کند.

### معیار تکمیل

Membership و چرخه حیات آن به‌صورت مستقل عملیاتی باشد.

## IAM-003 — نقش و مجوز

**حوزه:** دسترسی  
**اولویت:** Critical

### داستان کاربر

به‌عنوان مدیر شرکت، می‌خواهم نقش و مجوز هر کاربر مشخص باشد تا هر فرد فقط عملیات مجاز خود را انجام دهد.

### هدف

کنترل دقیق عملیات بر اساس نقش و سطح دسترسی.

### پیش‌شرط

عضویت فعال وجود داشته باشد.

### جریان اصلی

انتخاب نقش → اعمال مجوزها → امکان/عدم امکان عملیات → ثبت تغییرات.

### موارد مهم کسب‌وکاری

- حسابدار دسترسی گسترده مالی دارد اما مدیر سیستم نیست.
- مدیر مالی، مدیرعامل و کاربر عملیاتی مجوزهای متفاوت دارند.
- مجوزها باید هنگام عملیات Agent نیز اعمال شوند.

### معیارهای پذیرش

- هر عملیات حساس قبل از اجرا مجوز را کنترل کند.
- کاربر فاقد مجوز نتواند مسیر دستی یا Agentی را برای دورزدن محدودیت استفاده کند.
- تغییرات نقش Audit شوند.

### وابستگی‌ها

IAM-002، SEC-001

### معیار Agent

Agent نباید بیش از مجوزهای کاربر درخواست اجرا کند.

### معیار تکمیل

مدل نقش/مجوز در UI، Domain و Agent مشترکاً اعمال شود.

## IAM-004 — کنترل دسترسی در سطح شرکت

**حوزه:** Tenant Isolation  
**اولویت:** Critical

### پیش‌شرط

### معیارهای پذیرش

- تمام درخواست‌ها Company Scope داشته باشند.
- جستجو، گزارش، Agent و API از همین محدوده تبعیت کنند.
- هیچ شناسه داخلی قابل حدس نباید باعث دسترسی به شرکت دیگر شود.

### وابستگی‌ها

IAM-002، SEC-001

### موارد وابسته

RPT-001، AGP-002، SEC-002

### معیار ثبات داده

هیچ رکوردی نباید بدون Company Scope معتبر ایجاد شود مگر در موجودیت‌های صریحاً سراسری.

### معیار تکمیل

جداسازی شرکت‌ها در تمام مسیرهای خواندن و نوشتن اعمال شده باشد.

# 4. راه‌اندازی شرکت و مانده‌های افتتاحیه

## SET-001 — ایجاد و راه‌اندازی شرکت

**حوزه:** راه‌اندازی  
**اولویت:** Critical

### داستان کاربر

به‌عنوان مدیر شرکت، می‌خواهم شرکت را ایجاد و تنظیمات پایه آن را ثبت کنم تا محیط برای استفاده واقعی آماده شود.

### جریان اصلی

ایجاد شرکت → اطلاعات پایه → تنظیمات مالی → ایجاد دوره مالی → آماده‌سازی کدینگ.

### موارد مهم کسب‌وکاری

- شرکت باید قبل از ایجاد داده‌های مالی فعال باشد.
- تنظیمات قابل تغییر باید نسخه و Audit داشته باشند.

### معیارهای پذیرش

- شرکت فعال و قابل استفاده ایجاد شود.
- تنظیمات پایه معتبر باشند.
- تمام داده‌های جدید به شرکت صحیح متصل شوند.

### وابستگی‌ها

IAM-002، ACC-006، SYS-001

### مسیر طلایی

ایجاد شرکت → تنظیمات → دوره مالی → ورود به داشبورد.

### معیار تکمیل

شرکت از مرحله ایجاد تا آماده‌سازی برای ورود اطلاعات اولیه قابل استفاده باشد.

## SET-002 — ورود اطلاعات اولیه از Excel/CSV

**حوزه:** راه‌اندازی و Import  
**اولویت:** Critical

### داستان کاربر

به‌عنوان حسابدار، می‌خواهم اطلاعات اولیه را از فایل وارد کنم تا مجبور نباشم تمام اطلاعات شرکت را دستی وارد کنم.

### هدف

کاهش زمان مهاجرت شرکت به محصول.

### موارد مهم کسب‌وکاری

- قالب فایل باید قابل تشخیص و Mapping باشد.
- Preview و Validation قبل از ثبت الزامی است.
- خطاها باید به تفکیک ردیف و فیلد نمایش داده شوند.

### معیارهای پذیرش

- فایل قبل از ثبت اعتبارسنجی شود.
- داده معیوب مانع ثبت بخش معتبر به‌صورت ناگهانی نشود؛ رفتار تراکنشی و خطا روشن باشد.
- سابقه Import ثبت شود.

### وابستگی‌ها

SYS-002، MDM-001، ACC-006

### مسیر طلایی

آپلود → تشخیص ستون → Mapping → Preview → Validation → تأیید → ثبت → گزارش نتیجه.

### معیار سرعت

برای فایل‌های معمول یک شرکت، Preview و Validation باید در زمان قابل قبول عملیاتی انجام شود.

### معیار تکمیل

Import قابل تکرار، قابل Audit و قابل بررسی باشد.

## SET-003 — ثبت مانده‌های افتتاحیه

**حوزه:** حسابداری و راه‌اندازی  
**اولویت:** Critical

### داستان کاربر

به‌عنوان حسابدار، می‌خواهم مانده‌های افتتاحیه حساب‌ها، بانک، صندوق، دریافتنی، پرداختنی، موجودی و دارایی را ثبت کنم تا شرکت بتواند با مانده واقعی شروع کند.

### موارد مهم کسب‌وکاری

- مانده افتتاحیه باید با دوره مالی مرتبط باشد.
- سند افتتاحیه باید تراز باشد.
- ثبت افتتاحیه نباید تاریخچه شرکت را جعل کند.

### معیارهای پذیرش

- مجموع بدهکار و بستانکار تراز باشد.
- مانده‌های افتتاحیه در گزارش حساب‌ها و Flowهای وابسته منعکس شوند.
- هر ثبت قابل ردیابی باشد.

### وابستگی‌ها

ACC-007، ACC-008، SET-002، MDM-001

### مسیر طلایی

ورود مانده‌ها → Validation → ساخت سند افتتاحیه → تأیید → ثبت → مشاهده اثر.

### معیار ثبات داده

مانده افتتاحیه نباید باعث ایجاد سند نامتوازن یا مقدار موجودی ناسازگار شود.

### معیار تکمیل

شرکت پس از افتتاحیه قادر به شروع Flowهای عملیاتی باشد.

# 17. معیارهای تکمیل مشترک

هر User Story زیرساختی این سند زمانی کامل محسوب می‌شود که:

1. جریان اصلی آن عملیاتی باشد.
2. کنترل مجوز و Company Scope رعایت شود.
3. خطاهای اصلی قابل مشاهده باشند.
4. رفتار آن در Audit ثبت شود، هرجا که عملیات حساس است.
5. داده ایجادشده با مدل‌های مشترک محصول سازگار باشد.
6. در صورت ارتباط با Agent، مسیر Manual نیز وجود داشته باشد.
7. در صورت ارتباط با عملیات مالی، Idempotency و Recovery مناسب تعریف شده باشد.
8. معیارهای پذیرش Story با داده واقعی یا داده نزدیک به واقعیت تست شده باشند.

# 19. نتیجه

با ثبت Storyهای این سند، Gap Review دیگر یک لیست نیازمندی پراکنده نیست و به بک‌لاگ اجرایی مشترک تبدیل می‌شود.

از اینجا به بعد، User Storyهای اصلی MVP را می‌توان بدون تغییر مفهومی بزرگ به Issueهای فنی شکست؛ چون هسته مشترک، موتور اجرای عملیات، Agent Platform، Integration Platform و نیازهای امنیت/پایداری قبلاً به‌صورت مستقل مشخص شده‌اند.
