# 22 — Optimistic Concurrency

- وضعیت: پذیرفته‌شده
- نسخه: v1
- مرجع اجرا: `apps/backend/src/shared/persistence/` (SHR-008)

## 1. هدف

این سند مکانیزم مشترک کنترل همزمانی خوش‌بینانه را ثبت می‌کند تا چند عملیات همزمان که یک
وضعیت حفاظت‌شده را تغییر می‌دهند، آخرینِ نوشته را بی‌صدا برندۀ هم نکنند. یک نوشتن فقط
زمانی اعمال می‌شود که رکورد هنوز همان `Revision`ای باشد که نویسنده هنگام بارگذاری دیده؛
وگرنه رد می‌شود و برنده دست‌نخورده می‌ماند. مبنا ADR-004 (بخش ۲۷ — Concurrency Control)،
ADR-003 (مالکیت داده و مرز Persistence)، ADR-005 و قواعد Engineering 01/03/07/12 است.

این سند «سازوکار» را تعریف می‌کند، نه سیاست را: اینکه کدام رکورد، کدام عملیات و کدام قاعدهٔ
تجارتی نیاز به حفاظت دارد، تصمیم Domain مالک است.

**خارج از محدوده:** Locking توزیع‌شده، APIهای قفل خاصِ دیتابیس، استراتژی Pessimistic
Locking، قاعدهٔ تجاری خاصِ همزمانی، Staleness پلن اگنت (ADR-004، بخش‌های ۲۸–۲۹)، ترتیب
Event، همزمانی چنددیتابیسی و هماهنگی میکروسرویس.

## 2. مدل Revision

منبع: `shared/persistence/revision.ts` (SHR-004)

- یک عدد صحیح deterministic در بازۀ `1..2147483647` (`MAX_REVISION`)؛ رکوردِ تازه از
  `Revision.initial()` = ۱ شروع می‌شود.
- فقط یک چیز آن را عوض می‌کند: **یک نوشتن موفق**. نوشتنِ ناموفق هیچ اثری روی revision
  ندارد.
- هر نوشتنِ موفق دقیقاً یک واحد جلو می‌رود: `N → N+1`. هیچ شکافی بین نوشتن‌های موفق
  ایجاد نمی‌شود و در `MAX_REVISION` به‌جای Wrap، خطا می‌دهد.
- **هیچ معنی تجاری در revision نیست:** نه دورهٔ مالی، نه وضعیت سند، نه مالک و نه شمارهٔ
  سند. فقط و فقط پاسخ به این پرسش را می‌دهد: «ردیفی که خواندم هنوز همان است که می‌نویسم؟»
- revision متعلق به Storage است، نه به Domain: Aggregate مجبور نیست فیلد `revision`
  داشته باشد؛ اینکه کجا نگه داشته شود (کنار Aggregate، در Read Model یا در Use Case)
  تصمیم ماژول است.

## 3. بارگذاری وضعیت فعلی

منبع: `shared/persistence/repository-ports.ts` — `LoadsById.get(id)`

```text
get(id)  →  Loaded { aggregate, revision N }   یا   undefined   (نبودِ رکورد خطا نیست)
```

بارگذاری، نوشتنِ مشتق‌شده را همراه خود برمی‌گرداند. همین باعث می‌شود Application بتواند
بدون آنکه Domain را آلوده کند، نوشتن را به همان وضعیتی که دیده گره بزند. نبودِ رکورد
`undefined` است و اینکه آن را `NotFoundError` بدانیم یا مجوزِ ایجاد، تصمیم Use Case است
(سند ۱۶).

## 4. قرارداد بروزرسانی

منبع: `shared/persistence/repository-ports.ts` — `UpdatesAggregate.update(aggregate, expectedRevision)`

```text
خواندن وضعیت در revision N
        ↓
آماده‌سازی تغییر در Domain
        ↓
بروزرسانی فقط اگر revision == N
        ↓
موفق  →  revision N+1 و WriteReceipt
شکست  →  تشخیصِ همزمانیِ کهنه (stale)
```

- پارامتر `expectedRevision` **اجباری** است؛ قرارداد مسیری ندارد که بدون گفتنِ «کدام وضعیت
  را فعلی فرض می‌کنم» بنویسم، پس Last-Write-Wins در همان سطحِ قرارداد نمایان‌نشدنی است.
- **Check و Mutation یک گام‌اند.** Adapter باید مقایسه و نوشتن را در یک عملیات انجام دهد
  (یک `UPDATE ... WHERE revision = ?` روی MySQL؛ یک مقایسهٔ همزمان روی حافظه) تا هیچ
  نوشتنِ دیگری نتواند میانِ بررسی و اعمال فرو برود. بررسیِ جدا از اعمال، خودش یک Race
  Condition است.
- خروجی موفق `WriteReceipt` است با revisionِ تازه، پس «انجام شد» و «بعداً چه revision
  بخوانم» هیچ‌وقت مبهم نمی‌شود.

## 5. رفتار Stale Update

منبع: `shared/persistence/stale-revision.ts`، `shared/persistence/optimistic-concurrency.ts`

اگر `expectedRevision` با revision ذخیره‌شده یکی نباشد:

- **نوشتن باید شکست بخورد.**
- **رکوردِ موجود دست‌نخورده می‌ماند** — شکست، اثرِ جزئی یا نیمه‌کاره به جا نمی‌گذارد.
- **شکست قابل تشخیص است:** یک `PersistenceError` با `kind = CONFLICT` و
  `retryable = false` / `outcomeKnown = true`، که `cause` آن دادۀ سادۀ
  `StaleRevision { expected, actual? }` است.
- **از شکستِ اعتبارسنجی و خرابیِ زیرساخت جداست:** `ErrorCategory.CONFLICT` در برابر
  `VALIDATION`، و ترجمه به `ConflictError` مشترک.

 Adapter موظف است این شکست را از یک مسیر مشترک بسازد:

```ts
if (header.affectedRows === 0) {
  throw staleRevisionConflict('SalesDocuments.update', expectedRevision);
}
```

- `actual` اختیاری است: یک `UPDATE` که گزارش می‌کند «هیچ ردیفی نخورد» معمولاً نمی‌گوید
  الان چه چیزی ذخیره شده؛ حدس زدن، ناشناختهٔ صادقانه را به پاسخِ غلط تبدیل می‌کند.
- Domain هرگز `PersistenceError` نمی‌سازد؛ ساخت آن فقط در Adapter است.

## 6. تشخیص و ترجمه در لایه Application

| تابع | پاسخ |
| --- | --- |
| `isConcurrencyConflict(error)` | آیا این شکست، تداخل همزمانی است؟ (CONFLICT از هر مسیر) |
| `staleRevisionOf(error)` | `{ expected, actual }` پشتِ نوشتنِ کهنه، یا `undefined` |
| `toConflict(error)` | `ConflictError` مشترک، یا `undefined` وقتی چیزی برای ترجمه نیست |
| `PersistenceError.toDomainError()` | `CONFLICT` → `ConflictError`؛ بقیه فنی می‌مانند |

یک تداخل کهنه به `ConflictError` با `detail`ای از کد `STALE_REVISION` و `field: revision`
ترجمه می‌شود (اعداد `expected` / در صورت وجود `actual`)، پاسخ به Client هم می‌تواند
بگوید بر چه وضعیتی کار می‌شد، نه فقط یک عذرخواهیِ کلی. متنِ Driver، نامِ عملیات و `cause`
هرگز وارد پاسخ نمی‌شوند.

تصمیم بعدی با Application یا Domain مالک است: بارگذاری دوباره، درخواست بازبینی از کاربر،
بازسازی یا محاسبهٔ دوبارهٔ پلن، یا بازگرداندنِ Conflict به فراخواننده.

## 7. انطباق با قرارداد Repository

- این سند قراردادِ پورت را عوض نمی‌کند؛ پورت‌های SHR-004 همان‌هایی‌اند که بودند. آنچه
  اضافه شده، **سازوکار مشترکِ پیاده‌سازی آن‌هاست**: ساختنِ شکستِ کهنه و خواندنش.
- پورت، SQL و ORM را نمی‌شناسد؛ `persistence-conventions.spec.ts` توکنِ پیاده‌سازی را در
  سطحِ قرارداد رد می‌کند. رابطِ ماژول همچنان از `LoadsById` / `AddsAggregate` /
  `UpdatesAggregate` / `ChecksExistence` / `FindsByCriteria` ساخته می‌شود و `update` همچنان
  `expectedRevision` را اجباری دارد.
- Adapter می‌تواند MySQL/Drizzle باشد، یک Map در تست، یا هر چیز دیگر — بدون آنکه یک خط
  Domain یا Application عوض شود.
- هیچ API قفل خاصِ دیتابیسی وارد قرارداد نمی‌شود: نه `SELECT ... FOR UPDATE`، نه
  `LOCK IN SHARE MODE`، نه سینتکس خاصِ فراهم‌کننده. فقط یک شرطِ مقایسه‌ای روی revision.

## 8. انطباق با Transaction Boundary

منبع: `shared/transaction/` (SHR-005) و `infrastructure/database/scoped-database.ts`

- **بررسی همزمانی و خودِ تغییر، در یک مرز تراکنش‌اند.** Adapter از `scopedDatabase(...)`
  استفاده می‌کند، پس همان `UPDATE`ای که شرط revision را می‌سنجد، روی همان اتصالِ تراکنشِ
  Use Case اجرا می‌شود؛ چیزی میانِ بررسی و اعمال فاصله نمی‌گیرد.
- **شکستِ تداخل، کل مرز را برمی‌گرداند:** نوشتنی که برنده شده دست‌نخورده می‌ماند و هیچ
  اثرِ دیگرِ همان Use Case هم commit نمی‌شود (ADR-004، بخش ۱).
- مرز فقط تصمیم می‌گیرد **چه چیزهایی با هم commit می‌شوند**؛ اینکه نوشتن چطور اعتبارسنجی
  شود به همین قرارداد همزمانی برمی‌گردد و از آن جدایی‌ناپذیر است.
- هیچ Locking سمتِ کلاینت، هیچ صفِ انتظار و هیچ Retry حلقه‌ای داخلِ مرز وجود ندارد.

## 9. ممنوعیت Last-Write-Wins

الگوی زیر برای دادهٔ حفاظت‌شده ممنوع است و در قرارداد، مسیری برایش تعریف نشده است:

```text
Read A
Read B
Write A
Write B   ← B بی‌صدا A را overwrite نمی‌کند
```

رفتار درست:

```text
Read A (revision 10)
Read B (revision 10)
Write A → موفق، revision 11
Write B با revision 10 → رد می‌شود → CONFLICT → تصمیمِ Application
```

- `persistence-conventions.spec.ts` مسیرهای `upsert` / `save` / `merge` / `patch` را در
  قرارداد مسدود می‌کند.
- یک تست، چند نویسندهٔ همزمان را هم‌زمان اجرا می‌کند و می‌سنجد دقیقاً یکی برنده است.

## 10. رفتار Retry

- **زیرساخت هیچ‌وقت یک جهشِ تجاریِ شکست‌خورده را تکرار نمی‌کند.** تداخل،
  `retryable: false` است: نوشتن اعمال نشده و تکرارِ کورِ همان عملیات، یعنی اجرای دوبارهٔ
  یک اثر تجاری روی داده‌ای که حالا کهنه شناخته شده (ADR-004، بخش ۱۲).
- پاسخِ درست را Application یا Domain تصمیم می‌گیرد: بارگذاری دوباره، بازسازیِ عملیات،
  درخواست بازبینی از کاربر، محاسبهٔ دوبارهٔ پلن یا بازگرداندنِ Conflict به فراخواننده.
  حلقهٔ «دوباره بخوان، دوباره بنویس» نباید در Adapter، در Kernel یا در مرز تراکنش پنهان
  شده باشد.
- **تکرارِ صریح و آگاهانه با بارگذاریِ تازه** تصمیمِ Application است و کاملاً مجاز است؛
  آنچه ممنوع است تکرارِ خودکار و پنهان است.

## 11. داده‌های حفاظت‌شده

سازوکار برای داده‌های زیر قابل استفاده است — و انتخابِ اینکه کدام عملیات مشمول شود،
هیچ‌وقت در این لایه تصمیم گرفته نمی‌شود:

- سند مالی قبل از ثبت، جایی که وضعیتِ متغیر دارد.
- تراکنش‌های تجاری در معرضِ تغییر همزمان.
- وضعیت‌های حساسِ موجودی.
- پلن اگنت یا هر وضعیتی که اجرای کهنه باید رد شود.

سیاستِ حفاظتِ تجاری (کدام عملیات، کدام آستانه، چه واکنشی) متعلق به Domain مالک است.

## 12. تست‌ها

- `src/shared/persistence/stale-revision.spec.ts` — دادۀ سببِ کهنه، Guard و `ErrorDetail`.
- `src/shared/persistence/optimistic-concurrency.spec.ts` — قرارداد به‌طور کامل: بارگذاری
  با revision، ردِ نوشتنِ کهنه، پیشروی فقط با نوشتنِ موفق، چند نویسندهٔ همزمان با Barrier،
  قابل‌تشخیص‌بودنِ شکست، نبودِ Retry خودکار، و انطباق با مرز تراکنش.
- `src/shared/persistence/persistence-error.spec.ts` — ترجمهٔ `CONFLICT` به
  `ConflictError` همراه با جزئیاتِ revision کهنه.
- `test/optimistic-concurrency.e2e-spec.ts` (اختیاری، `MYSQL_INTEGRATION=1`) — همان قرارداد
  روی MySQL واقعی: دو تراکنش که یک ردیف را همزمان می‌خوانند، فقط یکی commit می‌شود؛
  تراکنشِ بازنده کامل rollback می‌شود؛ revision فقط یک واحد جلو می‌رود؛ و شکست به‌صورت
  تداخلِ قابل تشخیص بیرون می‌آید.

## 13. معیار پذیرش

- سازوکار مشترک `Revision` وجود دارد و وضعیتِ حفاظت‌شده می‌تواند revision فعلی خود را
  هنگام بارگذاری ارائه دهد.
- بروزرسانی می‌تواند revision مورد انتظار را اجباری طلب کند؛ فراخوانی بدون آن، قابل
  بیان نیست.
- revision کهنه باعث شکستِ بروزرسانی می‌شود و نوشتنِ شکست‌خورده وضعیتِ موجود را تغییر
  نمی‌دهد.
- بروزرسانیِ موفق، revision را طبق مدل تأییدشده جلو می‌برد (فقط یک واحد).
- اعتبارسنجی همزمانی و خودِ تغییر در یک مرز تراکنش رخ می‌دهند.
- قرارداد Repository مستقل از SQL و ORM باقی می‌ماند و هیچ API قفل خاصِ دیتابیسی وارد
  Domain یا Application نشده است.
- تداخل همزمانی از شکستِ اعتبارسنجیِ عمومی قابل تشخیص است (`CONFLICT` در برابر
  `VALIDATION`).
- رفتار Last-Write-Wins بی‌صدا برای دادهٔ حفاظت‌شده وجود ندارد.
- زیرساخت یک جهشِ شکست‌خورده را به‌صورت کور تکرار نمی‌کند.
- تستِ خودکارِ سناریوهای بروزرسانیِ همزمان پاسخ می‌شوند؛ typecheck و lint سبز است.
- هیچ سیاستِ تجاریِ خاصِ همزمانی به لایهٔ Shared اضافه نشده است.
