# 15 — Shared Kernel Primitives

- وضعیت: پذیرفته‌شده
- نسخه: v1
- مرجع اجرا: `apps/backend/src/shared/` (SHR-001)

## 1. هدف

این سند قرارداد Primitiveهای مشترک (Shared Kernel) را ثبت می‌کند تا هر ماژول
Domain از همان نمایش‌ها برای شناسه، مبلغ، تعداد و تاریخ استفاده کند و هیچ
ماژولی قواعد خودش را برای این مفاهیم اختراع نکند. مبنای تصمیم ADR-002 بخش ۱۰
(Shared Kernel) و قواعد Coding Standards بخش Domain است.

## 2. قواعد کلی

1. **وابستگی به Framework ممنوع است.** این پوشه فقط به `node:*` و فایل‌های خودش
   وابسته است؛ نه NestJS، نه Next.js، نه HTTP، ORM، Redis، MySQL یا SDK ارائه‌دهنده.
   `shared/framework-independence.spec.ts` این قاعده را روی کل پوشه بررسی می‌کند و
   نقض آن تست را قرمز می‌کند.
2. **هیچ Business Rule در اینجا وجود ندارد.** این انواع «شکل» را توصیف می‌کنند،
   نه «سیاست» را. `Quantity` جمع `kg` و `g` را رد می‌کند اما جدول تبدیل ندارد؛
   `BusinessDate` یک روز تقویمی است و از Fiscal Period خبری نیست.
3. **وضعیت نامعتبر رد می‌شود، نه ترمیم.** هر سازنده ورودی را اعتبارسنجی می‌کند و با
   `InvalidPrimitiveError` خط می‌زند؛ پیام همیشه Primitive و فیلد را نام می‌برد.
4. **`DomainError` برای شکست کسب‌وکار محفوظ است.** رد شدن یک Primitive خطای
   برنامه‌نویسی است، نه پاسخ قابل نمایش به کلاینت؛ بنابراین از `DomainError`
   استفاده نمی‌شود.

## 3. قرارداد هر Primitive

### شناسه — `id/entity-id.ts`

- `EntityId.generate()` یک UUID تولید می‌کند؛ `EntityId.from(value)` یک UUID موجود را
  می‌پذیرد و حرف‌ها را به حالت کانونیکال کوچک می‌کند.
- برابری مبتنی بر مقدار است و خروجی `toJSON()` یک رشتهٔ UUID خام است.
- شناسه هیچ معنای تجاری، نوع یا ترتیبی ندارد. ماژولی که به تفکیک اسمی نیاز دارد
  در لایهٔ خودش alias می‌سازد؛ Shared Kernel از هیچ ماژولی خبر ندارد.

### پول — `money/currency.ts` و `money/money.ts`

- `Money` مبلغ را به‌صورت عدد صحیح واحد کوچک (`bigint`) نگه می‌دارد؛ هیچ محاسبهٔ
  اعشاری مبتنی بر Float انجام نمی‌شود. ورودی عددی از نمایش دهدهٔ کوتاه‌ترین خودش
  خوانده می‌شود، پس `0.1 + 0.2` دقیقاً `0.3` است.
- مبلغ و ارز از هم جدانشدنی‌اند: ساخت `Money` بدون `Currency` ممکن نیست و جمع/تفریق
  بین دو ارز متفاوت با پیام صریح رد می‌شود.
- `add`، `subtract`، `multiply` و `divide` دارند. برای `multiply` و `divide`،
  `RoundingMode` الزامی است چون از دست دادن دقت باید در محل فراخوانی تصمیم آشکار
  باشد: `HALF_UP`، `HALF_EVEN`، `DOWN`، `UP`، `FLOOR`، `CEILING`.
- `Money.of` اگر مبلغ بیش از دقت ارز داشته باشد و `RoundingMode` ندهد، رد می‌کند.
- برابری مبتنی بر مقدار است؛ خروجی `toJSON()` همان قرارداد `MoneyDto` است:
  `{ amount: "125000", currency: "IRR" }` و هرگز عدد JSON نیست.

### ارز — `money/currency.ts`

- هر ارز یک کد ISO 4217 و یک `minorUnit` دارد (۰ تا ۴).
- MVP فقط `IRR` را ثبت می‌کند (minorUnit صفر بر اساس ISO 4217). افزودن ارز جدید یک
  فراخوانی `Currency.register(...)` است و به هیچ بازنویسی Domain نیاز ندارد؛ ثبت
  مجدد یک کد خطا می‌دهد.
- `Currency` نماد، locale یا قاعدهٔ نمایش ندارد تا به UI یا ماژول خاصی گره نخورد.

### تعداد — `quantity/quantity.ts`

- مبلغ دهدهٔ دقیق به‌علاوهٔ یک کد واحدِ مبهم (`unit` اختیاری).
- جمع/تفریق فقط داخل یک واحد مجاز است؛ مقادیر با scaleهای مختلف بدون از دست رفتن
  رقم با هم تراز می‌شوند.
- جدول تبدیل، قاعدهٔ معادل‌سازی واحد و هر قاعدهٔ محصول/انباری اینجا نیست.
- مقدار منفی و صفر مجاز است؛ سیاست موجودی منفی مالک دامنه است.

### تاریخ و زمان — `time/business-date.ts` و `time/date-time.ts`

چهار نقش زمانی دامنه حفظ می‌شوند و در یک نوع ادغام نمی‌شوند:

| نقش | نوع مشترک | نمایش |
| --- | --- | --- |
| Business Date | `BusinessDate` | `YYYY-MM-DD` بدون منطقهٔ زمانی |
| Accounting Date | `BusinessDate` | `YYYY-MM-DD` بدون منطقهٔ زمانی |
| Created At | `DateTime` | `2026-09-30T09:22:34.673Z` |
| Posted At | `DateTime` | `2026-09-30T09:22:34.673Z` |

- کدام فیلد کدام نقش را دارد، تصمیم ماژول مالک است و با نام‌گذاری فیلد بیان
  می‌شود؛ Shared Kernel هرگز آن‌ها را به یک چیز تبدیل نمی‌کند.
- `BusinessDate` به تاریخ‌های نامعتبر (۳۰ بهمن، ۲۹ اسفند در سال غیرکبیسه) و فرمت
  نادرست `YYYY-MM-DD` خطا می‌دهد. `addDays`/`subtractDays`/`diffDays` روی تقویم
  میلادی کار می‌کنند.
- `DateTime` فقط Instant است؛ `parse` منطقهٔ زمانی را اجباری می‌داند و هر offset
  معتبر ISO-8601 را به UTC نرمال می‌کند. نوشتن همیشه UTC با `Z` است.
- تبدیل Instant به روز تقویمی فقط با offset صریح (`toUtcDate` /
  `toDateInOffset`) انجام می‌شود؛ هیچ منطقهٔ زمانی پیش‌فرضی فرض نمی‌شود.

### اعتبارسنجی مشترک — `primitives/`

- `assert.ts` قواعد شکلیِ مشترک را نگه می‌دارد: رشتهٔ خالی، عدد صحیح خارج از بازه،
  الگو. همه با پیام `Primitive: فیلد ... ` خطا می‌زنند.
- `decimal.ts` حساب دهدهٔ دقیق روی `bigint`، شش `RoundingMode`، ترازسازی scale و
  قالب‌بندی رشته را ارائه می‌دهد. حداکثر ۱۸ رقم اعشار یک محدودیت ایمنی است، نه قاعده
  کسب‌وکار.
- `calendar.ts` قواعد تقویم میلادی و تبدیل UTC را بدون هیچ فرض منطقهٔ زمانی اجرا
  می‌کند.

## 4. نحوهٔ استفاده در یک ماژول Domain

```ts
import { Currency, Money, BusinessDate, EntityId } from '../../../shared/...';

const total = invoiceLine.price.multiply(invoiceLine.quantity, RoundingMode.HALF_UP);
const vat = total.multiply('0.10', RoundingMode.HALF_UP);
const issuedOn = BusinessDate.parse(payload.issuedOn);
const invoiceId = EntityId.generate();
```

ماژول باید:

1. نام فیلد را با نقش دامنه‌ای آن انتخاب کند (`businessDate`، `accountingDate`،
   `createdAt`، `postedAt`)، نه صرفاً نوع آن را.
2. `RoundingMode` را برای هر ضرب و تقسیم مالی صریح انتخاب و دلیلش را بداند.
3. هرگز `Money` را از عدد خام یا رشتهٔ بدون اعتبارسنجی نسازد.
4. قاعدهٔ کسب‌وکاری (سقف اعتبار، سیاست موجودی منفی، تبدیل واحد) را در ماژول خودش
   بنویسد، نه اینجا.

## 5. معیار پذیرش

- هر Primitive با واحد تست نرمال و حالت نامعتبر پوشش داده شده است.
- `framework-independence.spec.ts` روی کل پوشه پاس می‌شود.
- `pnpm verify` (typecheck، lint، format، تست، build) سبز است.
- هیچ موجودیت یا قاعدهٔ کسب‌وکاری به Shared Kernel اضافه نشده است.
