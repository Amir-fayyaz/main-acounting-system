# 1. Product Vision

محصول یک نرم‌افزار حسابداری و مدیریت عملیات مالی مدرن برای شرکت‌ها در ایران است که علاوه بر قابلیت‌های استاندارد حسابداری، Agentهای تخصصی را درون خود دارد.

هدف اصلی محصول کاهش کارهای تکراری و زمان‌بر حسابداران و تبدیل آن‌ها به فرایندهای قابل‌اعتماد، قابل‌کنترل و تا حد امکان خودکار است.

کاربر به جای انجام دستی تمام عملیات، از Agent درخواست انجام کار می‌کند. Agent عملیات پیشنهادی و اثر آن را مشخص می‌کند و پس از تأیید کاربر، عملیات را اجرا می‌کند.

اصل مهم:

**AI جایگزین کنترل حسابدار نیست؛ AI حجم کار حسابدار را کم می‌کند و اجرای عملیات را سریع‌تر می‌کند.**

# 2. Target Customer

### بازار اولیه

شرکت‌های ایرانی با حدود 20 تا 100 نفر نیروی انسانی، با MVP متمرکز بر شرکت‌های بازرگانی ساده.

نوع تجارت نباید در هسته محصول Hard-code شود.

محصول باید در آینده بتواند برای مدل‌های مختلف کسب‌وکار قابل توسعه باشد.

- کارکنان
- تعهدات مالی و قانونی

است.

# 4. Core Problem

مشکل اصلی:

**حسابدار بخش زیادی از زمان خود را صرف کارهایی می‌کند که تکراری، قابل پیش‌بینی و قابل استانداردسازی هستند.**

نمونه‌ها:

- ورود اطلاعات
- انتقال اطلاعات از فایل به سیستم
- ثبت سند
- تطبیق اطلاعات
- مغایرت‌گیری
- بررسی تراکنش‌ها
- کنترل حساب‌ها
- تهیه گزارش
- آماده‌سازی اطلاعات برای امور مالیاتی
- آماده‌سازی اطلاعات بیمه
- پیگیری عملیات دوره‌ای
- کنترل خطاها و ناقص بودن اطلاعات

هدف محصول این نیست که «حسابداری را حذف کند».

هدف این است که:

```text
Manual Work
     ↓
Agent-assisted Work
     ↓
Human Approval
     ↓
Controlled Execution
```

# 5. Agent Model

Agentهای محصول باید به جای یک Chatbot عمومی، Agentهای تخصصی باشند.

برای مثال:

### Accounting Agent

پیشنهاد:

- ثبت سند
- اصلاح سند
- طبقه‌بندی تراکنش
- بررسی سند
- ایجاد سند از روی اطلاعات ورودی

### Reconciliation Agent

پیشنهاد:

- تطبیق بانک با حسابداری
- پیدا کردن مغایرت
- پیدا کردن تراکنش‌های بدون تطبیق
- پیشنهاد اصلاح

### Invoice Agent

از:

- PDF
- Excel
- تصویر فاکتور

اطلاعات را استخراج و ساختارمند می‌کند.

سپس می‌تواند پیشنهاد دهد:

```text
Supplier
Invoice Number
Date
Items
Quantity
Unit Price
Tax
Total
Accounts
Suggested Accounting Entry
```

### Reporting / Control Agent

مثلاً:

- پیدا کردن موارد غیرعادی
- پیدا کردن اطلاعات ناقص
- بررسی عملیات روزانه
- پیشنهاد اقدام

# 6. Agent Execution Model

Agent نباید بدون کنترل کاربر عملیات مالی حساس را اجرا کند.

مدل اصلی MVP:

```text
User Request
      ↓
Agent Analysis
      ↓
Planned Actions
      ↓
User Review
      ↓
User Approval
      ↓
Execution
      ↓
Result
      ↓
Audit Trail
```

مثلاً:

> «تراکنش‌های بانک دیروز را بررسی کن.»

Agent:

```text
17 تراکنش پیدا شد.

12 مورد با اسناد موجود تطبیق داده شد.
3 مورد احتمالاً مربوط به مشتری X هستند.
1 مورد نیازمند بررسی حسابدار است.
1 مورد تکراری تشخیص داده شد.

پیشنهاد اجرای 12 عملیات:
[مشاهده جزئیات] [تأیید اجرا]
```

این الگو باید تبدیل به یکی از اصول اصلی UX محصول شود.

# 7. Input Channels

در MVP ورودی‌های زیر مهم هستند:

### PDF

برای فاکتور، اسناد و مدارک

### Image

برای تصویر فاکتور و اسناد

### Excel

برای ورود یا انتقال اطلاعات ساختاریافته

### Manual Entry

برای اطلاعاتی که نیاز به ورود مستقیم دارند

در مراحل بعد می‌توانیم Integrationهای دیگر اضافه کنیم.

«فایل حسابداری» را فعلاً وارد Scope نمی‌کنیم. منظور از آن معمولاً فایل‌هایی است که نرم‌افزارهای حسابداری دیگر برای Import/Export استفاده می‌کنند؛ این موضوع بیشتر در مهاجرت از سیستم قبلی، انتقال اطلاعات یا Integration اهمیت پیدا می‌کند.

- بستن دوره
- اصلاحات

### Sales

- فروش
- فاکتور
- دریافتنی

### Purchase

- تأمین‌کننده
- خرید

### Cash & Bank

- بانک
- صندوق
- دریافت
- پرداخت

- چک
- مغایرت

### Inventory

- کالا
- انبار

- انتقال
- موجودی

### Expense

- هزینه‌ها
- اسناد هزینه
- پرداخت

### Employee / Payroll-related

به اندازه‌ای که برای عملیات مالی و تعهدات شرکت لازم باشد.

### Tax & Compliance

- اطلاعات موردنیاز مالیاتی
- آماده‌سازی
- کنترل
- ارسال / Integration در صورت فراهم بودن زیرساخت

- اطلاعات حقوق و دستمزد مرتبط

- کنترل

برای نمونه، سازمان تأمین اجتماعی در حال حاضر ارسال لیست و پرداخت حق بیمه کارفرمایان را از طریق سامانه خدمات غیرحضوری خود پشتیبانی می‌کند؛ بنابراین این بخش را در Discovery به‌عنوان یک Integration/Compliance workflow مستقل در نظر می‌گیریم، نه صرفاً یک صفحه داخل حسابداری.

همین موضوع درباره عملیات مالیاتی و صورتحساب الکترونیکی نیز صادق است؛ الزامات سامانه مؤدیان و صورتحساب الکترونیکی باید به‌عنوان یک حوزه‌ی مستقل از هسته حسابداری مدل شوند.

# 9. Management Needs

در حال حاضر لازم نیست همه نیازهای مدیرعامل یا مدیر مالی را قطعی بدانیم. اما برای MVP یک مجموعه پایه باید داشته باشیم.

### مدیرعامل

وقتی وارد سیستم می‌شود باید بتواند سریع بفهمد:

- الان چقدر نقدینگی داریم؟
- چقدر از مشتریان طلب داریم؟
- چقدر به تأمین‌کنندگان بدهکاریم؟
- فروش چقدر است؟
- هزینه‌ها چقدر است؟
- سود تقریبی/قطعی چقدر است؟
- پرداخت‌های مهم پیش‌رو چیست؟
- وصولی‌های مهم پیش‌رو چیست؟
- چه مواردی نیازمند توجه من هستند؟

مدیرعامل نباید مجبور شود گزارش حسابداری را بخواند تا این اطلاعات را استخراج کند.

### مدیر مالی

مدیر مالی علاوه بر موارد بالا باید بتواند:

- وضعیت عملیات مالی را کنترل کند.
- عملیات در انتظار تأیید را ببیند.
- مغایرت‌ها را مشاهده کند.
- خطاها و داده‌های ناقص را پیدا کند.
- وضعیت حساب‌های بانکی را کنترل کند.
- بدهکاران و بستانکاران را بررسی کند.
- وضعیت بستن دوره را ببیند.
- فعالیت حسابداران را کنترل کند.
- عملیات انجام‌شده توسط Agentها را بررسی کند.

# 10. MVP Boundary

در MVP قرار نیست «تمام امکانات نرم‌افزارهای حسابداری دنیا» ساخته شود.

هدف MVP:

**یک شرکت بازرگانی ساده بتواند چرخه اصلی مالی خود را مدیریت کند و بخش قابل‌توجهی از کارهای تکراری حسابدار را Agentها انجام دهند.**

بنابراین MVP باید روی این جریان‌ها تمرکز کند:

```text
Input
 ↓
Understand
 ↓
Validate
 ↓
Suggest
 ↓
Approve
 ↓
Execute
 ↓
Reconcile
 ↓
Report
```

نه روی تعداد زیاد صفحه‌ها و Featureها.

# 11. Success Metrics

دو معیار اصلی محصول:

## Speed

اندازه‌گیری زمان انجام عملیات.

مثلاً:

```text
Manual:
ثبت یک فاکتور = X دقیقه

With Product:
ثبت یک فاکتور = Y دقیقه
```

اما فقط زمان کلی کافی نیست.

باید اندازه بگیریم:

- زمان ورود اطلاعات
- زمان بررسی
- زمان تأیید
- زمان مغایرت‌گیری
- زمان تهیه گزارش
- زمان انجام عملیات دوره‌ای

## Consistency / Data Quality

باید بفهمیم داده‌ای که سیستم تولید می‌کند چقدر قابل اعتماد و پایدار است.

مثلاً:

- درصد اطلاعات صحیح استخراج‌شده
- درصد تطبیق صحیح تراکنش‌ها
- درصد سندهای بدون اصلاح انسانی
- تعداد خطاهای تکراری
- تعداد Duplicate
- تعداد عملیات برگشت‌خورده
- اختلاف بین داده ورودی و داده ثبت‌شده

برای Agentها یک معیار بسیار مهم دیگر هم اضافه می‌کنیم:

**Approval Rate**

یعنی چند درصد پیشنهادهای Agent بدون تغییر توسط حسابدار تأیید می‌شوند.

# 12. اصل محصول

من پیشنهاد می‌کنم این را به‌عنوان اصل اصلی Product نگه داریم:

> **هر جا یک حسابدار امروز مجبور است یک کار تکراری، قابل‌قاعده و قابل‌بررسی را به‌صورت دستی انجام دهد، باید بررسی کنیم آیا می‌توان آن را به یک Agent سپرد.**

اما:

> **هر جا تصمیم مالی حساس، مبهم یا پرریسک است، Agent باید قابل مشاهده، قابل توضیح و قابل تأیید توسط انسان باشد.**
